The Cheap Feature Is Never Cheap

  • DATE: November 25, 2026
  • AUTHOR: Chris Amato
  • CATEGORY: Process

AI cut the cost of building software complexity. It did not cut the cost of living with it.

A Drupal workflow for a university newsroom began as three steps: draft, review, publish. Then came more roles, department-scoped permissions, revision handling, a separate queue for featured stories, scheduling, approval gates, exceptions to those gates, and a way through when the news could not wait.

ChatGPT helped turn each scenario into a requirement. Cursor turned the requirement into something the stakeholders could click through, on a budget that would once have bought a fraction of the system. Someone would try the result and say, "Yes, but what if..."

It worked. That is the problem.

The cost of writing the code fell. The cost of living with the workflow did not.

Saying yes got cheaper

In the old arrangement, that last sentence met a number. A developer would say it was another forty hours, and explain why. The estimate forced a decision about what mattered.

An assistant can shrink the same change to an afternoon. The conversation the estimate used to require gets shorter, and then it stops.

When a feature was expensive, someone had to justify it. When a feature became relatively easy, that justification became easy to skip. I was the person who made the next request easy to accept.

Owning it did not

  • Editors have to tell approval, publication, scheduling, and promotion apart.
  • Administrators have to know who can do what, and why.
  • Managers have to know who owns an exception.
  • New people need training, and that training has to change when the rules change.
  • The people who depend on the system have to test it. An automated suite does not do that job.

There is a second set of costs, easier to miss: explaining behavior nobody expected, settling a permission dispute, revisiting a policy, and living with the distance between the workflow someone described and the way the newsroom actually works.

A workflow is not a set of transitions between database states. It is an organizational process encoded in software. Encoding it might take days. Absorbing it can take months.

A convincing prototype stops looking like one

The demo did what a prototype should do. Stakeholders could see the states, try the permissions, find the contradictions, and revise what they wanted. An assistant is unusually good at that kind of exploration.

Then the prototype stopped being treated as a prototype. People stopped asking whether a feature was necessary and started adjusting how it behaved. Each demonstration turned up another exception. Accommodating it was easy, so the question of whether to accommodate it hardly came up.

A working feature shows that something can be built. It has not shown that the organization needs it, understands it, or benefits from it. A careful build of a workflow that should not exist in that form is still a bad outcome. A more convincing prototype can make that outcome more likely.

Every safeguard is reasonable alone

In a large institution, people carry real responsibilities, and some of them have reason to fear a bad day. Each person wants the system to protect their team. Each safeguard looks sensible on its own.

One person wants an approval gate. Another wants an exception to that gate. Someone else wants scheduling limited to a few roles. Then comes the night when the limit has to be set aside.

Taken one at a time, these are reasonable. Together they can produce a brittle system, built to cover every imagined contingency before anyone has used it.

The rules were still changing while they were being built, for a release that was still months away. The organization was still learning how it wanted to work. That learning was being written into the software as quickly as it appeared.

Once a change is cheap, deciding every case in advance starts to feel responsible. The organization still has to live with every decision that gets made.

The tools did not cause this

Organizations were overbuilding software long before language models. Requirements have always been a way to feel that the bad day has been handled. Some of the complexity here is legitimate. Scoped access, protection for unpublished revisions, and real publication permissions are institutional duties.

The same tools exposed contradictions that might have stayed hidden until people were depending on the system. Found earlier, those ambiguities were cheaper to fix.

AI does not cause the overbuilding. It changes the price of saying yes. A team can explore many more possibilities, much faster, without paying the old cost to build them. The scarce work moves from producing the software to judging it.

Ship the floor

For the first release, almost none of the prototyped workflow needs to ship.

These do:

  • Basic publishing controls. Draft, review, publish.
  • Essential access restrictions. Who may see unpublished work, and who may make it public.
  • Integrity and rollback. A mistake has to be recoverable.

Past that, complexity has to justify itself. The elaborate demo can stay a reference. It does not have to be the system people learn on the first day.

Let the newsroom work. Notice where approval actually slows someone down, which exceptions come up often, and which feared cases never arrive. Some of the elaborate rules will be necessary. Some will not survive contact with a real week. Some are better handled by training, by an agreed convention, or by a conversation.

A workflow the newsroom can understand may be the better product. Further rules can be added because someone has seen the need.

These tools are unusually good for trying a change, watching it, and revising it. Using them to specify every contingency before anyone has done the work gives that advantage back to an older habit.

Deploy by a different standard

Software that publishes news, and that people rely on during a working day, is a poor place to optimize for a longer feature list.

Stability is a feature. So is knowing what will happen after a click on Publish.

Prototype freely. Use an assistant to explore ideas that used to cost too much to try. Decide what to deploy by a stricter standard than the one used to decide what to prototype.

Being able to build a workflow in a few days says almost nothing about whether anyone should have to learn it.

The demo already settled whether the elaborate version can be built. What it left open is which of those rules a newsroom should have to understand and maintain before anyone has worked a week in the simple one.
