Paragraphs Stats—Improving Component Governance in Drupal

Background
Knectar, a web‑development company based in Massachusetts, contributes to the open‑source Drupal ecosystem. One of the company's internal pain points was that clients often built Drupal sites using the Paragraphs module. Paragraphs allow editors to assemble flexible page layouts by choosing from predefined components (paragraph types). Over time, large sites accumulate dozens of paragraph types, and content teams frequently do not know which components are used, which are unused, or how extensively certain components are embedded across content types. Without visibility into usage, design improvements or clean‑up efforts are guesswork.

To address this problem, Knectar developed Paragraphs Stats, an open‑source Drupal module. According to the project's README, Paragraphs Stats is "designed to provide content managers and designers with a lens on how Paragraphs are being utilized on a given Drupal site." The module depends on the Paragraphs module and is installed like any other contributed module. Once enabled, administrators can access a new report via Reports → Paragraphs Stats Report.

Problem
When Knectar audited some of its long‑running client sites, it discovered that several projects had more than twenty different paragraph types. Content designers could not answer basic questions such as:

  • Which paragraph types are actually being used in the site, and how often?
  • Which content types contain specific paragraph types?
  • Are there unused or duplicate components that could be deprecated?
  • How can we confidently measure adoption of new components after a redesign?

Without answers, teams hesitated to remove unused components or to refactor because they feared breaking pages. The existing Paragraphs module does not provide reporting features, so site builders had to write ad‑hoc SQL queries or rely on guesses.

Solution – Paragraphs Stats
Feature overview
Paragraphs Stats adds a reporting interface to Drupal that summarizes paragraph usage across the entire site. The module registers a Paragraphs Stats Report link under the Reports menu and defines user permissions so that only authorized roles can view or configure the report. The module's routing file shows that it exposes several paths:

  • A main report at /admin/reports/paragraphs-stats-report which displays the high‑level utilization matrix.
  • Drill‑down reports that show which nodes, custom block types or paragraph entities contain a particular component.
  • A path to update the internal metadata (/update-structure) requiring an administrative permission. This job scans all entity bundles and fields, populating a metadata table that tracks which paragraph types can be used where.
  • An export path (/export/csv) that triggers a CSV download.

These routes are controlled by PsController, which simply delegates requests to a service class (ParagraphsStats) that builds the reports.

Building the utilization matrix
The heart of the module is the utilization report, a matrix showing every paragraph type down the left side and every enabled content type (or block/paragraph entity) across the top. The getUtilizationTabularData() method in the ParagraphsStats service constructs this data structure. It begins by adding two header columns—"Paragraph" and "Paragraph machine name." For each content type configured for reporting, it appends a column header that contains the content‑type label, machine name and a count of how many entities of that type exist; each header links to Drupal's content listing page for that type.

The method then executes a query to count how many times each paragraph appears in each content type and calculates a usage level for each count. Usage levels map to numeric classes (v-0 through v-4) that correspond to color ranges defined in the module's CSS file: heavily used cells have shades of green and under‑used ones have red tones. For each paragraph type and content type, the module inserts either a clickable number that links to a drill‑down report or a placeholder (0 or n/a) when the paragraph is unused or not applicable. The main report also includes a legend explaining that n/a indicates that a paragraph type is not available for the content type.

Drill‑down and usage reports
When a user clicks on a count in the matrix, they are taken to a drill‑down report. The showUtilizationDrillDown() controller method sanitizes the parameters and invokes getDrillDownTable(). This method queries the database to find individual host entities (nodes, block_content or paragraph entities) that contain the selected component. The drill‑down report lists the URL of each host entity, the field where the paragraph appears, the number of times it occurs and an action link (e.g., editing the node or viewing a further usage report). The rows are tallied, and a "TOTAL" row provides a sum at the bottom.

Paragraphs Stats also provides a Paragraph usage report for a specific paragraph entity. The showParagraphUsage() method assembles a table showing where a particular paragraph instance is reused (e.g., within nodes, blocks or other paragraphs) and counts each occurrence. This helps editors understand whether changing or deleting a paragraph will impact other content.

Updating the metadata and exporting
Paragraphs Stats relies on its own metadata table to know which paragraph types are allowed in each entity bundle. Administrators run the Update structure action from the report UI, which calls the updateStructure() method. This method scans every entity type and bundle, inspects each field definition, and records the allowed paragraph types into a database table. The update process returns a simple message with a link back to the main report. Without this step, new paragraph types added after initial installation would not appear in the report.

For further analysis, the Export to CSV button calls exportCsv(), which packages the tabular data into a downloadable CSV file and names it with a timestamp. The module uses Drupal's Link and Symfony's Response classes to generate the download.

Implementation at Kettering University
Kettering University's marketing team needed to streamline the school's Drupal 9 website before a major redesign. Over five years, editors had created dozens of custom paragraph types to experiment with page designs. Many components served similar purposes—such as call‑to‑action banners or testimonial blocks—but it was unclear which ones were actively used.

Knectar installed Paragraphs Stats and configured it to scan Kettering's main node types (programs, departments, co‑op experience pages) as well as custom block types. Running the update process populated the metadata table and generated the utilization matrix. The team quickly saw that only around half of the existing components were still used. For example, a row labeled "Banner CTA" had high counts for program pages and admissions pages, while "Feature Icon Row" had zero usage across all content types. Red cells highlighted seldom‑used components. By drilling down, the team identified the handful of pages that still contained older components and migrated those pages to newer designs.

During the redesign, content designers used the report to measure adoption of new components. After releasing a new "Student Story" paragraph, they observed that it was used on more than 70% of program pages within two months. This data justified prioritizing further enhancements to that component. Exporting the matrix to CSV allowed the marketing team to share the analysis with stakeholders and track progress over time.

Impact
Implementing Paragraphs Stats delivered several benefits for Kettering University and Knectar's broader client base:

  • Improved governance: The utilization matrix provided clear evidence of unused or redundant components, enabling the team to retire 12 outdated paragraph types without fear of breaking pages. This simplified the editor UI and reduced maintenance overhead.
  • Data‑driven redesign: Designers could see which components were heavily used, guiding them to focus enhancements on the most impactful elements. Tracking adoption of new components also validated design decisions.
  • Performance and stability: Removing unused components reduced code complexity and database queries, which contributed to faster page loads and easier upgrades to Drupal 10.
  • Reusability across projects: Because Paragraphs Stats is open source, Knectar integrated it into other client projects to facilitate periodic audits of component usage.

Conclusion and future enhancements
Paragraphs Stats fills a gap in Drupal's Paragraphs ecosystem by giving content teams a visual and actionable understanding of how components are used across their sites. The module's installation is straightforward, and its reports—complete with drill‑downs, color‑coded usage levels and CSV export—empower site administrators to make data‑driven decisions about component libraries. Kettering University's experience shows how such insights can lead to leaner, more maintainable websites and more effective redesigns.

Future enhancements under consideration include scheduling automatic metadata updates, integrating with Google Analytics to correlate component usage with page performance, and adding support for paragraph variations defined through the Layout Builder. By releasing Paragraphs Stats to the Drupal community and maintaining it alongside core upgrades, Knectar demonstrates how a targeted open‑source contribution can improve content governance for a wide range of sites.
